1
Prompt bar + pills are additive, not either/or — free text ("sunday morning coffee") and toggled pills (Calm, Focus) both feed one query. Matches parso‑acalum's DiscoveryContext pattern, mapped onto this app's existing DiscoverySearchQuery(text:positiveRefinements:…).
2
"Play a mood" starts a continuous queue, not a static result list — no manual playlist‑building step. Reuses AudioPlayer.play(tracks:startAt:source:), the exact call every other row‑tap in the app already uses.
3
Screen 02's "matched" chips show which selected pills the current track actually scored on — plain‑language accountability for why a track was picked, not a black box.
4
Jump Back In / Stats / Favorites move down, not away (screen 03) — same progressive‑disclosure precedent as this session's Settings redesign. Nothing becomes unreachable.

What's new

Prompt bar, pill row, "Play a mood" CTA, the Now‑Playing‑a‑mood view, "Shake it up." A MoodPill data type (id, label, query term) drives the pill row from one editable list.

What's reused, untouched

CLAP text embedding, DiscoverySearchViewModel's query pipeline, FlowChips' styling precedent, Keep Playing's queue‑extension logic. "Find by sound" keeps working exactly as it does today as the precise‑filter path.

Open before building

Real pill taxonomy needs a content pass against an actual library. Continuous‑queue extension source and the exact CLAP/tag scoring blend both need reading the real implementation first — see the plan doc's §5.
