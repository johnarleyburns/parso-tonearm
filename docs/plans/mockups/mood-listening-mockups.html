Platterhead / Tonearm — Design Note

Mood‑Based Listening

Four states for a redesigned Listen tab: a prompt‑bar‑and‑pills entry point replacing the current stats‑first landing screen, adapted from parso‑acalum‑ios‑app's proven pattern and built entirely on this app's existing on‑device CLAP semantic search — plus tappable Top 10 lists and a detail card that replaces instant‑play‑on‑tap everywhere. No new model, no new network dependency.

1
Prompt bar + pills are additive, not either/or — free text ("sunday morning coffee") and toggled pills (Calm, Focus) both feed one query. Matches parso‑acalum's DiscoveryContext pattern, mapped onto this app's existing DiscoverySearchQuery(text:positiveRefinements:…).
2
"Play a mood" starts a continuous queue, not a static result list — no manual playlist‑building step. Reuses AudioPlayer.play(tracks:startAt:source:), the exact call every other row‑tap in the app already uses.
3
Screen 02's "vibing with" chips echo the pills currently selected — context for what's shaping the queue, not a per‑track "why this matched" claim. Audited: the scoring data (RankBreakdownDisplay.Component) has no per‑refinement‑term attribution, so a true causal "matched: X" explanation isn't something the current infrastructure can actually support — worded honestly instead of overclaiming.
4
Jump Back In / Stats / Favorites move down, not away (screen 03) — same progressive‑disclosure precedent as this session's Settings redesign. Nothing becomes unreachable. Stats now list Top 10 Songs and Top 10 Artists, not one name each — every row is tappable.
5
Tapping any track opens this card instead of playing instantly (screen 04) — owner feedback: instant‑play‑on‑tap felt jarring with no information shown first. Every action reuses an existing AudioPlayer call (playSingle/appendToQueue) already wired to today's long‑press context menu — this promotes them to the primary tap, it doesn't invent new playback logic. Cross‑cutting: applies to My Music and search results too, not just Listen (see plan §3.6). Shown here with all four actions for illustration — "Include in current mood" only actually appears when a mood is already playing (AudioPlayer.shared.queueSource == .mood); tapping a track with nothing playing shows just Play Now / Add to Queue / Dismiss.

What's new

Prompt bar, pill row, "Play a mood" CTA, the Now‑Playing‑a‑mood view, "Shake it up," tappable Top 10 Songs/Artists lists, and a TrackDetailCard sheet (Play Now / Add to Queue / Include in current mood / Dismiss) that replaces instant‑play‑on‑tap everywhere. A MoodPill data type (id, label, query term) drives the pill row from one editable list.

What's reused, untouched

CLAP text embedding, DiscoverySearchViewModel's query pipeline, FlowChips' styling precedent, Keep Playing's queue‑extension logic, and AudioPlayer.playSingle/appendToQueue — already wired to today's long‑press context menu, just promoted to the primary tap. "Find by sound" keeps working exactly as it does today as the precise‑filter path.

Open before building

Real pill taxonomy needs a content pass against an actual library. Continuous‑queue extension source and the exact CLAP/tag scoring blend both need reading the real implementation first. Rolling TrackDetailCard out to My Music/search results is a deliberate follow‑up, not bundled with the Listen tab work — see the plan doc's §5.
